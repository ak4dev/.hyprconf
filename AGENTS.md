# Agent Instructions

The one rule file for this repo. `README.md` is the user contract; `docs/CONTRIBUTING.md` holds the layout tree, the test tree, the publish flow and the website upload. All three must stay true to the code.

## Project vision (the north star)

hyprconf is the overlay `README.md` opens with — **`install.sh` plus the shipped payload, layered onto a stock [Omarchy](https://omarchy.org) install through Omarchy's own tools and seams**: hotkeys, look'n'feel, monitor presets, bar widgets, shell, theme bridges, a menu row and `bin/` tools, disturbing that install as little as possible. Omarchy owns the base system; hyprconf never competes with it. When a change could be read multiple ways, choose the reading that best upholds these principles:

1. **Use Omarchy's own tools.** Every job Omarchy already has a command, seam or mechanism for is done through that — see the first repo rule below. A hand-rolled replacement is a drift bug, not a feature.
2. **Extend only through documented seams.** A user theme under `~/.config/omarchy/themes/`, a user template under `~/.config/omarchy/themed/` (rendered by Omarchy's own template engine on every theme set), a shell plugin (or a copy of a built-in one, the way `omarchy plugin clone` makes it), a hook installed with `omarchy hook install` under `~/.config/omarchy/hooks/*.d/`, a Hyprland toggle file under `~/.local/state/omarchy/toggles/hypr/` (the directory Omarchy's own `omarchy-hyprland-*` toggles write to, loaded after the user files), a managed block in the menu extension file `~/.config/omarchy/extensions/omarchy-menu.jsonc` (the one user file the menu merges over its defaults), an `include` appended to a config Omarchy owns (kitty), the `~/.config/hypr/{bindings,input,looknfeel}.lua` files Omarchy `require`s *after* its defaults, a session-environment file under `~/.config/uwsm/env.d/` (the user-override seam `/usr/share/uwsm/env.d/10-omarchy` names), and the "personal configuration" tail of `~/.config/hypr/hyprland.lua`. A program Omarchy has an installer for comes through it (`omarchy-install-browser firefox`, `omarchy-install-editor-vscode`). Nothing writes to `/usr/share/omarchy`, changes the login shell, or runs `pacman` itself: `omarchy-pkg-add` installs, and the one removal — Arch's `code`, which conflicts with Omarchy's VS Code package — is `omarchy-pkg-drop`. `sudo` happens in three stages, all behind the `--no-packages` gate and never without a terminal for the password prompt: packages, Firefox (Omarchy's installer plus the merged system policy, `/etc/firefox/policies/policies.json` — the overlay's one write outside `$HOME`; Firefox reads enterprise policies only from root-owned paths, and that path shadows the `distribution/` file Omarchy writes, hence the merge) and VS Code (Omarchy's installer). Nothing else touches `/etc`; `hyprconf-yubikey`, run by the user, adds its kernel parameters through a `/etc/limine-entry-tool.d/` drop-in the way Omarchy's hibernation setup does.
3. **Never work from memory about Omarchy.** Re-derive every claim from the running system (rule below).
4. **Idempotent, reversible, set-once for user choices.** Every `install.sh` stage re-runs safely and byte-stably; the post-update hook re-applies the overlay after every `omarchy-update`, so anything that is a *choice* — font, default apps, clock format, workspaces widget, active theme, the monitor layout in use — is applied once (or never) and left to the user from then on. Every stage has a stock-restoring undo (`.stock` backups, `omarchy plugin disable`, `hyprconf-monitor-preset stock`, `hyprconf-yubikey disable`, `hyprconf-vulkan-gpu remove`, managed-block markers; the hooks and the template are plain files to delete).
5. **Private by default.** The Firefox policy ships telemetry off and uBlock Origin force-installed, on top of Omarchy's own prefs; nothing phones home; **official Arch repositories, plus Omarchy's own `[omarchy]` repository through an Omarchy installer — never an AUR helper** (rule below). A change may add privacy, never reduce it.
6. **Tests and docs move in lockstep.** Hermetic unit + integration suites, CI green, no PII. See the audit principles.
7. **Posture: a personal config shared as-is.** One person's daily-driver setup, published as reference and inspiration — not a maintained product, with no support or feature-request obligation. Favour removing scaffolding over adding it. `web/` is a static page hosted manually on S3.

**Decision rule for any change:** does Omarchy already do it? does it go through a documented seam? was it verified against the installed Omarchy? is it idempotent and reversible, and does it leave user choices alone? is it hermetic, tested, documented in the README, and free of PII and of any package outside the package rule? If any answer is "no", reshape the change until they are all "yes".

## Audit principles (the standing bar for every change)

Every change — feature, fix, or refactor — must satisfy **all** of these, **in the same commit**:

1. **Tests move in lockstep with features.** Adding or changing a stage, flag, script, config path, package, hotkey, preset or plugin means adding or updating its tests in the same commit, in the right suite (`unit` / `integration`); every new or changed code path is covered. When a change intentionally alters behaviour, update the affected test to assert the **new** contract and say so in the commit message — never silently weaken, delete or loosen a test to get a green run; if a test fails for any other reason, fix the code, not the test.
2. **Docs move in lockstep too.** `README.md` is the primary source of truth for every agent working here, so drift is a correctness bug, not a documentation gap. It keeps 1:1 parity with the code: every stage, flag, package, hotkey, preset, plugin id, `bin/` tool, path and behavioural detail is reflected, and nothing appears that no longer exists. A README review is a non-optional step of every change: grep `README.md` for what you touched and fix anything that describes the old behaviour. Keep it concise — every section earns its place; tables and code blocks over narrative. **Never alter the branding block** (banner SVG + badges) at the top. This file keeps the same parity. `web/index.html` is a hand-maintained static reflection, not a mirror.
3. **Tests stay hermetic.** The contract is under **Testing & CI** below: no test may reach the desktop, the system or the real repository.
4. **Restraint invariants never regress.** Never `chsh`; never rewrite Omarchy's `kitty.conf` beyond the one `include`; never point `omarchy-default-terminal` at a terminal that is not installed (it checks nothing — `stage_terminal` asserts kitty first); never call `pacman` (`omarchy-pkg-add` installs; the one removal, Arch's `code` before Omarchy's VS Code installer, is `omarchy-pkg-drop`); never switch the active theme; never replace Omarchy's `monitors.lua`; never overwrite a seeded preset; never re-assert a set-once choice; never write outside `$HOME` except the Firefox policy. `tests/unit/test_omarchy_install.py` asserts these.
5. **Hygiene.** `shellcheck` and `ruff` clean; no dead code and no dead directories (remove an unused one — git history preserves it); no committed artefacts; no PII. Favour deleting over adding: every line ships to a user's `$HOME`, so anything not needed to deploy the overlay — a tool, a library module, a test, a doc section — goes.
6. **GitHub CI must always be green.** Every push must leave `.github/workflows/test.yml` passing; a red run on `dev` or `stable` is a release blocker, and `dev` is never promoted to `stable` while any workflow is red. Reproduce CI locally before every push (**Testing & CI**).

## Repo rules

- **ALWAYS use Omarchy's own config tools and binaries when possible.** Before writing any custom mechanism — a script, a config edit, a file copy — check whether Omarchy already ships a command or seam that does the job (`omarchy commands --json`, `/usr/share/omarchy/bin/`, `omarchy bar set`, `omarchy-pkg-add` / `-drop` / `-present`, the `omarchy-install-*` installers, themes, user templates under `~/.config/omarchy/themed/` and `omarchy theme refresh`, shell plugins, `omarchy plugin clone` and `omarchy-shell shell rescanPlugins`, `omarchy hook install`, the Hyprland toggles directory, the menu extension file `~/.config/omarchy/extensions/omarchy-menu.jsonc`) and use that instead. A hand-rolled replacement for something Omarchy already does is a drift bug: it bypasses Omarchy's own state, OSDs and migrations, and breaks on its next release. A custom path is acceptable only where Omarchy demonstrably has no tool for the job, and the code comment must say so, citing what was checked.

- **Never work from memory about Omarchy — check the running system and the current docs before every change.** This repo sits on a system it does not own and cannot pin: Omarchy ships breaking changes between releases, and every assumption about its files, commands, defaults or seams is a drift bug waiting to happen. An "obvious" fact that was true when a doc was written is not evidence. Before writing, reviewing or reasoning about anything here:

  1. **Read the installed source.** `/usr/share/omarchy/` is authoritative for the version this machine runs (`omarchy version`, `/usr/share/omarchy/version`). Read it freely; **never edit it** — the package owns it and an update overwrites it. `default/hypr/*.lua`: the Hyprland defaults the overlay layers onto (`helpers.lua` defines `o.bind`; `bindings/*.lua` shows which keys Omarchy binds, and which by **keycode**) — diff against them before adding a setting, since restating a value Omarchy already sets creates drift the moment it retunes the default. `config/`: the templates a fresh `$HOME` is seeded from (`omarchy refresh config <path>` re-copies one — through a symlink, see the quirks). `bin/`: what a command really does, guards and exit codes included (`cat "$(which omarchy-theme-set)"`); several check less than they appear to (quirks). `shell/`: the Quickshell plugin contract — `Ui/BarWidget.qml` (the base every bar widget extends), `README.md` and `plugins/README.md` (the manifest contract), `services/PluginRegistry.qml` (`clonedFrom` resolution), `plugins/panels/clock/` (the one plugin `install.sh` copies and patches), `plugins/bar/widgets/` (the stock `Workspaces.qml` / `ActiveWindow.qml` the overlay's `clonedFrom` plugins replace — re-read when Omarchy changes the widget contract).
  2. **Enumerate from the machine, never from memory.** `omarchy commands --json` lists every route with its group, args, aliases and `requires_sudo`; `omarchy <group> --help` documents one. Confirm a command exists and takes the arguments you think it does before calling it, and prefer the documented `omarchy <group> <action>` form over the underlying `omarchy-*` binary. Where the overlay needs a list of Omarchy's commands, themes, plugins, fonts or presets, **derive it at runtime from those commands** — a generated list tracks Omarchy, a hard-coded one rots.
  3. **Re-verify against the published manual** at <https://omarchy.org/manual/> whenever a change touches user-facing behaviour or a documented seam. The chapters the overlay overlaps: Monitors, Keyboard/Mouse/Trackpad, Themes, Making your own theme, Hotkeys, Shell Plugins, Toggles/Idle/Screensaver, Omarchy CLI, Backgrounds, Fonts, Dotfiles, Common tweaks, Updates.
  4. **Record what you checked.** Name the Omarchy version the change was verified against in the commit message, and cite the specific file or command that justifies each claim about Omarchy's behaviour, the way the existing comments do (`omarchy-theme-update` skipping a symlinked theme dir — its `[[ ! -L ]]` guards `git pull` — while `omarchy-theme-set`'s `-d` test and `cp -r` follow the link, which is why a symlinked user theme works; the ALPM AbortOnFail hook; `omarchy-refresh-config`'s `cp -f` through a symlink). A claim about Omarchy with no traceable source is not verified.

  This binds documentation and review as much as code: a "fix" premised on stale knowledge of Omarchy is a regression even when the diff looks right.

- **Packages: official Arch repositories, plus Omarchy's own `[omarchy]` pacman repository when the package comes through an Omarchy installer — never an AUR helper.** Every package this project installs automatically, on any code path (`install.sh`, `packages`, or anything added later), must come from an official Arch repository, with one sanctioned exception: a package from Omarchy's own `[omarchy]` repository (`pacman -Si <pkg>` → `Repository: omarchy`) installed through the Omarchy installer that owns it (`omarchy-install-editor-vscode` → `visual-studio-code-bin`), never by naming it in `packages` or handing it to `omarchy-pkg-add` directly. Never `yay`, `paru`, `makepkg` or `omarchy-pkg-aur-add`, on any path: Omarchy ships `yay`, uses the AUR itself and exposes `omarchy-pkg-aur-add`; that is not permission — hyprconf does not reach for the AUR because the host platform does. If a feature appears to require an AUR package, **stop and raise it with the user, and verify the package, before implementing anything** — do not add it, do not add an AUR helper call, and do not quietly pick an AUR-only dependency to make a feature work; AUR packages remain something the user installs manually, by choice. Enforced by the scans in `tests/unit/test_omarchy_install.py` (no `makepkg` or `omarchy-pkg-aur-add` in the code; `pacman` never runs).

- **Never commit PII.** No real names, emails, hostnames, IPs, MAC addresses, serial numbers, API keys/tokens, AWS account IDs or secrets, or absolute paths containing the user's home directory (e.g. `/home/<user>`) may appear in tracked files — configs, docs, scripts, or commit messages. Everything the overlay installs lands in any user's `$HOME`, so it uses `~`, `$HOME`, `$USER`, a placeholder (`testuser`, even in test fixtures) or a runtime substitution (`@HYPRCONF_DIR@` in the hooks and `bin/` tools). Enforced across **every tracked file** by `tests/unit/test_no_pii.py`, which derives the identities to search for — login name, home directory name, hostname, git email — from the environment at runtime, so the guard itself never has to name them. This is also why plugin copies use the `hyprconf.*` id namespace rather than `omarchy plugin clone`'s `<username>.<id>`.

- **The web frontend is a static page, not an app.** `web/` is a single self-contained `web/index.html` (plus `favicon.svg`; the screenshot placeholder it and the README show is `assets/screenshot.svg`) — no React, build step, test suite, or bundler, and no external CDN/font requests (privacy). It exists so others can see what the project is: a static reflection of the README, framed impersonally ("a personal Hyprland setup, shared as-is"). Do not reintroduce a framework, a build, or tests, and do not grow it into a docs app.

- **Hosting is the existing AWS S3 + CloudFront — kept, but managed manually.** `hyprconf.sh` is the `hyprconf-sh` S3 bucket behind a CloudFront distribution whose User-Agent router serves browsers the `index.html` object and `curl`/`wget` the `install.sh` object — the page's `bash <(curl -fsSL hyprconf.sh)` runs that file, whose `bootstrap` clones `stable` into `~/.hyprconf` and hands over to the checkout's copy. The router is infrastructure outside the repo and nothing in the repo deploys: the live site is updated by hand, and the `install.sh` object is always **`stable`'s**, uploaded after `scripts/publish` (lint + test → promote `dev` to `stable`, no deploy step), never the `dev` copy. The four objects, their content types, the invalidation and the verification are under "Updating the website" in `docs/CONTRIBUTING.md`. Do **not** rebuild a CDK app, a deploy CLI, or a React frontend; `infra/` holds only the system Firefox policy.

## Layout

The full tree is in `docs/CONTRIBUTING.md`. `install.sh` is the only entry point — served as-is by `hyprconf.sh`, so with no payload beside it (`hypr/`, `packages`) `main()` hands over to `bootstrap` (the curl path, `README.md` › Install); `--help` and unknown options answer before any clone. The `.hyprconf` banner (`banner()`, the rows of `assets/banner.svg`) prints once per run, on a terminal only, and **never clears the screen** — the hook runs the script inside `omarchy-update`, whose output must stay on screen. Every stage is idempotent and byte-stable across re-runs, user choices are set once behind a marker in `~/.local/state/hyprconf/`, and everything the script touches is reachable by the suite: `$HOME` is relocated wholesale, and the `_HYPRCONF_*` seams (`OMARCHY_PATH`, `PKG_ADD`, `ZSH_BIN`, `ZSH`, `KITTY_BIN`, `FIREFOX_POLICIES`, `ASSUME_TTY`, `PLUGIN_WAIT`) name what lies outside it — binaries and system paths. Never create files under `~/.config/` by hand — add them to the repo and wire them through a stage. Logic that does need Python lives in `lib/hyprconf/` as a bounded, tested module (`firefox_theme.py` is the model), never as an inline `python3 -c` / heredoc; the package is used in place from the checkout (`PYTHONPATH` set by the theme-set hook and `bin/hyprconf-firefox-theme`), nothing is copied or linked into `~/.local/lib`. `infra/firefox/policies.json` lives in `infra/` because it targets a system path, not `$HOME` (installed merged over Omarchy's own policy); `themed/` holds the user templates Omarchy's engine renders (`stage_themed`). Not user-facing: `web/`, `tests/`, `scripts/publish`, `docs/`, `.github/`. Nothing is packaged: users `git clone -b stable` (or run the curl one-liner, which does that clone for them), and the promoted branch is the release, dev-only paths and all.

## Workflow, commits, versions

- All regular work happens on `dev`; `stable` is written only by `scripts/publish`, which promotes `dev` → `stable`. Never push directly to `stable` unless the user explicitly asks.
- **Never push to any remote unless the user explicitly asks.** Commit locally and wait for "push"; the only exception is an instruction that unambiguously includes one ("commit and push").
- **Never run `scripts/publish` unless the user explicitly says to publish** — it promotes `dev` to `stable` and creates a release tag, a deliberate, user-directed action.
- Run `make test` after every change, before committing; never commit code that fails tests. Every commit includes the tests and README updates for the code it touches — a feature without tests is unverified, and one without README coverage is invisible.
- Every install-time fix is idempotent and re-applied by the post-update hook, which runs `install.sh --no-update --no-packages` after every `omarchy-update`: a fix that only works on a fresh run, needs sudo, or is not byte-stable across re-runs is incomplete. Set-once choices go behind a marker in `~/.local/state/hyprconf/`.
- **Commit messages are [Conventional Commits](https://www.conventionalcommits.org/)**: `<tag>(<scope>): <message>`, subject line ≤ 140 characters; scope optional but encouraged (`install`, `hotkeys`, `plugins`, `monitors`, `zsh`, `docs` …); breaking changes add `!` to the tag and/or a `BREAKING CHANGE:` footer; name the Omarchy version the change was verified against. Tags: `feat` (new user-facing functionality), `fix`, `docs`, `style` (formatting only), `refactor` (no feature or fix), `perf`, `test`, `build` (deps/tooling), `ci`, `chore`, `revert`.
- **[Semantic Versioning](https://semver.org/)**: `__version__` in `lib/hyprconf/__init__.py`, bumped by `scripts/publish` — PATCH for `fix`/`docs`/`perf`/`refactor`/`style`/`test`/`build`/`ci`/`chore`, MINOR for any `feat`, MAJOR for `feat!`/`fix!` or a `BREAKING CHANGE:` footer (removed or renamed hotkeys, stages, flags, plugin ids or paths).

## Packages

- Every binary the overlay needs on a fresh Omarchy goes in `packages`, in a commented section saying which hotkey/stage wants it. Things already in Omarchy's base (`eza`, `zoxide`, `fastfetch`, `yay`, `ttf-jetbrains-mono-nerd-basic`, `xdg-terminal-exec`, `foot` …) are deliberately **not** listed; nor is a program Omarchy has an installer for (Firefox, VS Code — `stage_firefox`, `stage_editor`), which goes through that installer. An orphan package is not a free one: remove it when the hotkey that wanted it goes.
- `install.sh` parses the file itself (strips `#` comments and whitespace) and hands the list to `omarchy-pkg-add`, which is idempotent (`omarchy-pkg-missing` guard, `pacman -Q` verify) and fails on a package conflict (`pacman -S --noconfirm --needed`). Removal is `omarchy-pkg-drop`, and only where an Omarchy installer's package conflicts with an installed one (Arch's `code` vs `visual-studio-code-bin`). Never call `pacman`, `yay`, `makepkg` or `omarchy-pkg-aur-add`.
- Confirm the package name and repository with `pacman -Si <pkg>` (`Repository: core|extra`, or `omarchy` behind an Omarchy installer) / `pacman -Qo <binary>` before adding it (package rule above).

## Keybindings

- All hotkeys live in `hypr/bindings.lua`, loaded by Omarchy's `~/.config/hypr/hyprland.lua` *after* its defaults. `mainMod` is `SUPER`; do not redefine it. One bind per line — it keeps the file diffable and greppable.
- Bind with `o.bind(keys, description, dispatcher, options)` — Omarchy's helper from `default/hypr/helpers.lua` — never bare `hl.bind`: only `o.bind` records the description `omarchy-menu-keybindings` (`SUPER+K`) lists. A string dispatcher becomes `hl.dsp.exec_cmd(...)`.
- Every key hyprconf takes over is **unbound first** (`rebind()` does `hl.unbind` + `o.bind`): Hyprland does not replace a bind on a repeat of the same combo — both fire. Digits and `-`/`=` need `unbind_keycode()` (quirks).
- Launch apps through Omarchy's launchers, named the way Omarchy's own bindings name them — `o.bind(keys, desc, { omarchy = "terminal" })` is `omarchy-launch-terminal` (`default/hypr/helpers.lua`, `command_from`; `bindings/applications.lua`) — never a binary name, so the user's defaults follow. hyprconf's own tools are bound by command name (`"hyprconf-gaps +"`), the way Omarchy binds its commands: `stage_bin` puts `bin/hyprconf-*` on `~/.local/bin`, which is on the session PATH, and nothing under `~/.config/hypr/` is executed (`test_config_exec_targets.py`). A hotkey that launches a program not in Omarchy's base adds it to `packages`.
- Never restate a bind Omarchy already has (`default/hypr/bindings/*.lua`): `SUPER+P`, `SUPER+arrows`, `SUPER+scroll` and `SUPER+LMB/RMB` drag are Omarchy's own (`tiling.lua`) and `test_hypr_overrides.py` fails on a copy of them — a restated bind is drift the moment Omarchy retunes it.
- Volume, brightness and media keys, `SUPER+K`, `SUPER+SPACE` and `SUPER+3`/`4` are left to Omarchy on purpose. `SUPER+D` is hyprconf's: Omarchy binds nothing there (its menu key is `SUPER+SPACE`), and hyprconf puts `omarchy-menu toggle` on it.

## Scripts

- `#!/usr/bin/env bash` and `set -euo pipefail`, except where the comment beside the `set` line says why: the two hooks drop `-e` (`omarchy-hook` must never see an update or a theme switch abort), `bin/hyprconf-yubikey` drops `-e` (every step reports its own failure), and `bin/hyprconf-stats` is `set -u` (a long-lived sampler that must survive a transient read failure). A script that deviates without that comment is a bug.
- Runtime Hyprland changes go through `hyprctl eval` and `hyprctl dispatch 'hl.dsp.…'` — `hyprctl keyword` and `dispatch dpms on` are dead under the Lua parser (quirks).
- Hotkey-launched scripts have no visible stdout: report through `omarchy-osd` and `omarchy-notification-send`. No `pkill` or `killall` in new scripts.

## Monitor presets

- Presets live in `hypr/` as `pcMonitors.<name>.lua` (plus `pcMonitors.lua` = `pc` and `laptopMonitors.lua` = `laptop`); `install.sh` **seeds** them into `~/.config/hypr/` once and never overwrites them. `bin/hyprconf-monitor-preset` copies the chosen one (never a link) to `~/.local/state/omarchy/toggles/hypr/hyprconf-monitor-preset.lua` — Omarchy's Hyprland toggles directory, which `config/hypr/hyprland.lua` requires (`default.hypr.toggles`, line 26; `require_all` with `reload`) after `hypr.monitors` (line 19), so a later `hl.monitor` wins — the seam `omarchy-hyprland-monitor-internal` writes its own toggle to — then `hyprctl reload`; `stock` is `rm -f` + reload. Omarchy's `monitors.lua` is never touched (a v4.0.0–v4.2.0 symlink there is migrated once by `migrate_monitors_symlink`). Each preset carries its own `hl.workspace_rule` lines, one per line — the tool parses them to move existing workspaces after the reload.
- Adding a preset: the file in `stage_monitors`' seed list, the name in `hyprconf-monitor-preset`'s usage line, a hotkey in `hypr/bindings.lua` (`o.bind`, with `hl.unbind` first) if it deserves one, a row in `README.md`, and a test in `tests/unit/test_monitor_preset.py` / `test_omarchy_install.py`.

## Testing & CI

- Two suites, and they are the whole suite — there is no VM or install suite; behaviour that needs a live Omarchy session is verified by hand on the machine and recorded in the commit message (Omarchy version, command, file). `tests/unit/`: `install.sh` via fake `omarchy-*` bins in a throwaway `HOME` (every stage, the curl bootstrap against a throwaway clone, the banner, the restraint invariants, idempotency), the `bin/` tools (the two hotkey tools included), the `hypr/*.lua` deltas, `firefox_theme.py`, the zshrc block, and the Firefox-policy, config-target and PII guards. `tests/integration/`: `scripts/publish` — `--help`, `--dry-run` and the real promotion — against a throwaway bare origin. `make test` runs both (`-n auto`); the per-file tree is in `docs/CONTRIBUTING.md`.
- **Hermetic, always.** Both suites pass in a minimal `archlinux:latest` container as root — no running Hyprland or Omarchy shell, no real hardware, configured services, real `$HOME` or group memberships, no ambient state, never mutating the container (`pacman` exists there but is never invoked). Every path a script-under-test reads is under a relocated `$HOME` or behind an env seam (`: "${_VAR:=/default}"`, never `readonly` — `_HYPRCONF_*` in `install.sh` for what lies outside `$HOME`, `_HYPRCONF_*` in `bin/hyprconf-yubikey` for the boot files it reads and writes (`MKINITCPIO_D`, `LIMINE_DEFAULT`, `LIMINE_CONF_D`, `VCONSOLE`, …), `_HYPRCONF_*` in `bin/hyprconf-vulkan-gpu` for the sysfs trees and env files it reads (`SYS_PCI`, `SYS_DRM`, `UWSM_ENV_D`, `ENVIRONMENT_D`, …), `HYPRCONF_STATS_*` / `HYPRCONF_GPU_*` in the feeders) pointed at a `tmp_path`. Every command that could touch the desktop or the system is **always** a fake bin first on `PATH`, with no exception — and **`/usr/bin` carries a copy of every `omarchy-*` command** (426 on 4.0.0-1), so a PATH of fakes plus `/usr/bin` still reaches the real ones: every `omarchy-*` a code path can call is stubbed (`_setup` in `test_omarchy_install.py`) or named through a seam. Pure tools are real when present and the test skips (`pytest.skip`) otherwise, inside a throwaway tree under `tmp_path` — never the repository the suite runs from; `omarchy-plugin-validate` (reads a manifest, changes nothing) is the one real `omarchy-*` command a test runs, from `/usr/share/omarchy/bin`. A test that reads a file of the installed Omarchy (`test_firefox.py`'s policy merge) falls back to the install suite's fixture of that file rather than skipping, and — when Omarchy is there — checks the fixture against the real file. The lists and the pattern are under "Writing hermetic tests" in `docs/CONTRIBUTING.md`. Ambient state — real `id`/group membership, a git identity, an installed package, a TTY — is injected (`_HYPRCONF_ASSUME_TTY`), never assumed. Fixtures use `~`, `$HOME`, `testuser`.
- **CI runs as root**, and root bypasses DAC checks: a test that asserts an operation *fails* on an unreadable/unwritable path — any `[[ -r ]]` / `os.access` / mode-bit check — can pass as your user yet flip as root. Gate such logic on the euid (`(( EUID == 0 ))` / `os.geteuid() == 0`) and reproduce as root before trusting a green local run: `unshare -r python -m pytest <file>`.
- `.github/workflows/test.yml` runs on every push and PR to any branch, two jobs in `archlinux:latest`: **Lint** (`make shellcheck` + `make lint`) and **Unit + Integration** (`make test`; the container gets `jq`, `shellcheck`, `lua` and `qt6-declarative` (`qmllint`) so the tests that use the real ones do not skip, and `diffutils` for the `cmp` `install.sh` runs — Omarchy has it through mkinitcpio, the bare container does not). **Exactly one test skips in CI**: `test_installed_plugins_pass_omarchy_plugin_validate`, which needs the installed `/usr/share/omarchy/bin/omarchy-plugin-validate` (no package provides it in the container); it runs on every Omarchy box, so run the suite locally before a push. Any other skip in CI is a regression. Reproduce before every push with `make lint && make shellcheck && make test`, or in the container itself — the `podman` recipe is under "CI" in `docs/CONTRIBUTING.md`.
- Coverage is local only — `pytest --cov=hyprconf` with `python-pytest-cov`, config in `pyproject.toml`; CI does not run it, so check it yourself and do not let it regress.

## Known codebase quirks

- **Firefox applies `--lwt-*` / `--toolbar-*` userChrome overrides only under a lightweight theme** — under the default (system) theme the same `userChrome.css` does nothing, so `firefox_theme.py` sets `extensions.activeThemeID` to the built-in Dark/Light theme and also paints the chrome by id. Both files are read at Firefox startup only.
- **Bash 5.3 `$(< file 2>/dev/null)` is broken** — the redirect breaks the `$(<)` special form, returning empty. Use `read -r var < file` (no fork) or `$(cat file 2>/dev/null)`.
- **Number keys 3/4 are NOT bound to workspaces** — F1/F2 are used instead; `SUPER+3`/`SUPER+4` keep Omarchy's binds and `SUPER+SHIFT+4` is the screenshot key.
- **`hyprctl keyword` is a silent no-op on Hyprland 0.56** — prints "keyword can't work with non-legacy parsers" and exits 0, and `dispatch dpms on` is a 0.55-ism that errors under Lua. Runtime changes go through `hyprctl eval` (reports failure, exit 7) and `hyprctl dispatch 'hl.dsp.…({ … })'` — the forms are under "Runtime" in `docs/hyprland-reference.md`. `hyprconf-gaps` reads the gap with `hyprctl getoption -j` + `jq` (the way Omarchy's own scripts do) and writes it with `eval`.
- **Omarchy binds digits and `-`/`=` by keycode** (`SUPER + SHIFT + code:20`, `code:10…21`), which `hl.unbind` of the keysym does not match — Omarchy's bind stays live and both fire. `unbind_keycode()` (`KEYCODE` table in `bindings.lua`) is load-bearing.
- **`omarchy-default-terminal <t>` checks nothing** — it writes the desktop id into `~/.config/xdg-terminals.list` and notifies, so pointing it at an absent terminal leaves `SUPER+RETURN` and every TUI launcher with no terminal; `stage_terminal` asserts kitty exists first. `omarchy-install-terminal` prints "Failed to install" and exits 0, so it is never used.
- **`omarchy plugin clone` hardcodes `<username>.<id>`** — a username in shipped config is PII, so `install.sh`'s `copy_builtin_plugin` makes the one copy of a stock plugin (`hyprconf.clock`, plugin-directory layout only) with the same `clonedFrom` manifest rewrite; `hyprconf.workspaces` and `hyprconf.active-window` are the overlay's own plugins shipped with `clonedFrom` already in their manifests. The registry swaps a `clonedFrom` copy into the stock entry at enable time only, and `shell.json`'s `bar.centerAnchor` does no clone resolution, so `install.sh` moves it after the clock swap (`docs/quickshell-reference.md`).
- **`omarchy refresh config hypr/<file>` / `omarchy refresh hyprland` write through the override symlinks into the checkout** — `cp -f` follows links (observed on Omarchy 4.0.0-1). `restore_clobbered_override` puts a byte-identical stock template back from git (`bindings`, `input`, `looknfeel`; `monitors.lua` is Omarchy's own real file). Keep the symlinks (the manual's dotfiles chapter recommends stow-style links) and keep the guard.
- **`omarchy-theme-set-templates` renders nothing on its own once a theme is set** — it reads and writes only `~/.local/state/omarchy/current/next-theme`, the staging dir `omarchy-theme-set` builds under its lock and `mv`s to `current/theme` (`omarchy-theme-set:139-165`), and is called from nowhere else (`:156`). Re-rendering the current theme is `omarchy-theme-refresh` (`omarchy theme refresh`: `omarchy-theme-set` of `theme.name` with the wallpaper kept) — `stage_themed` uses it, and every theme set leaves every rendered template in `current/theme`, so `firefox_theme.py` never renders: with no `current/theme/userChrome.css` it exits 1 naming that command (the file is missing only with no theme, no template, or a failed refresh). `test_firefox_theme.py` stubs the three theme commands to prove the bridge calls none of them — it runs inside `omarchy-theme-set`'s own hook fan-out. `light.mode` is the legacy light marker; Omarchy 4.0.0-1's light themes carry `mode = "light"` in `colors.toml`, which is why the template renders `{{ mode }}` rather than the bridge guessing.
- **`omarchy-install-editor-vscode` opens VS Code once and exits with that launch's status** (no `set -e`) — `stage_editor` reads the result back with `omarchy-pkg-present`. `omarchy-pkg-add` is `pacman -S --noconfirm --needed`, which a package conflict fails: Arch's `code` goes first, through `omarchy-pkg-drop` (removes only names `pacman -Qq` lists).
- **`/etc/firefox/policies/policies.json` shadows `/usr/lib/firefox/distribution/policies.json`**, the file `omarchy-install-browser` writes. A policy of the overlay's own would silently drop Omarchy's prefs (VA-API, fractional scaling, overscroll), so `stage_firefox` installs `jq -s 'reduce .[] as $layer ({}; . * $layer)'` of Omarchy's `default/firefox/policies.json` then `infra/firefox/policies.json` — ours wins on a shared key; `test_firefox.py` checks the superset against the installed Omarchy.
- **Bar widgets: never size off `parent`** — the bar's ModuleSlot takes its height from the widget's implicit size, so `parent.height` closes a binding loop and QML drops it, leaving an invisible widget. Bind `implicitHeight` to content.
- **Never use `git update-index --skip-worktree`** — it hides files from the working tree while keeping them tracked; clear with `git update-index --no-skip-worktree <file> && git checkout -- <file>`.
- **Branding: `.hyprconf` vs `hyprconf.sh`** — the project name is stylised as **`.hyprconf`** (leading dot) except for the domain (`hyprconf.sh`), binary names (`hyprconf-*`) and plugin ids (`hyprconf.*`).
